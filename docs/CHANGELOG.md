# Журнал изменений бэкенда

Что менялось в API и в документации и зачем. Источник истины по контракту —
[openapi.yaml](openapi.yaml) (раздел Changelog в его описании — по версиям). Здесь — то, чего
в контракте не видно: уточнения описаний, исправленные данные и ответы на вопросы без
изменений API.

Новые записи — сверху. Метки:
- **API** — изменилось поведение или контракт;
- **Docs** — изменилось только описание в openapi, поведение прежнее;
- **Данные** — правка данных на проде;
- **Ответ** — вопрос, по которому API не менялся.

---

## 2026-10-21 · openapi 1.19.0

**API** `GET /requests`:
- `status` принимает несколько значений через запятую или массивом:
  `?status=Approved,Completed`, `?status[]=New&status[]=Rejected`. Один статус работает как раньше.
  Неизвестные значения игнорируются; если известных не осталось — пустой список, без ошибки.
- `?search=` — поиск по номеру запроса, грузу (`cargo_name`) и названию клиента среди **всех**
  видимых пользователю записей. Подстрока, регистр не важен. Число, в том числе с `№` или `#`,
  ищется и как точный номер запроса. Работает вместе с фильтрами и пагинацией, видимость не
  расширяет.
- Сортировка: `created_at DESC`, при равенстве — `id DESC`. Записи одной секунды больше не
  переезжают между страницами.

## 2026-10-20 · openapi 1.18.1

**API** `GET /requests` и `GET /contragents` принимают `limit` (и `page`). Раньше размер страницы
был всегда 20, хотя параметр был описан. Верхняя граница `limit` (в openapi — 100) пока не
проверяется ни в одном списке.

**Docs:**
- У `GET /requests` появилось описание: кто что видит (Admin/Supervisor — всё, Logist —
  назначенные ему, Sales/Ops — созданные ими), что в списке есть и переданные в работу заказы.
- Параметр `initiator_id` в `GET /requests` работает только для Admin/Supervisor, остальным
  молча игнорируется — они и так видят только свои записи. Так было и раньше, теперь написано.
- `POST /orders/{id}/request-route-change`: Ops имеет доступ и к заказам, переданным ему
  (`ops_manager_id`), а не только к созданным им. Код был верный, исправлен текст.

## 2026-10-20 · openapi 1.16.0–1.18.0 — чеклист бэкенду от 09.10

### 1. Перестановка этапов маршрута (1.16.0)

**API** `PUT /requests/{id}/route/reorder`:
- Принимает **все** этапы маршрута. Неполный список или чужой ID → **409** `Route Changed`,
  `details.missing_stage_ids` / `details.unknown_stage_ids`: маршрут изменился с момента
  загрузки. Раньше чужой ID давал 404, неполный список — 500 с частично записанным порядком.
- Пройденный этап (есть хотя бы одна фактическая дата) нельзя сдвинуть с его позиции → **422**
  `Cannot Reorder Stage`, `details.locked_stage_ids`. Непройденные вокруг него — свободно.
  Раньше 422 был, если пройденный этап вообще присутствовал в списке, то есть после `reopen`
  перестановка не проходила никогда.
- Повтор ID в `stage_ids` → 422.
- Все записи в маршрут (добавление, правка, удаление, перестановка этапа) — в транзакции под
  блокировкой заказа: при ошибке ничего не записывается наполовину.

**API** `POST /requests/{id}/route` больше не принимает `stage_order` → 422. Новый этап всегда
встаёт в конец, место ему задаёт reorder.

**Данные** Заказ №78: порядок этапов возвращён к исходному — 84, 85, 86, 87 (временные
отрицательные номера от неудачной перестановки убраны).

### 2. Запрос на завершение заказа (1.17.0)

**API:**
- `POST /orders/{id}/request-completion`, тело `{ "updated_at" }`. Только Ops, которому передан
  заказ (`ops_manager_id`); Admin/Supervisor — 403 (завершают сразу через `complete`). Только для
  `Approved`. Ответ — заказ целиком (201). Повтор при уже стоящей отметке — 200, время первого
  запроса сохраняется, `updated_at` в этом случае не проверяется.
- Поля `completion_requested_at` и `completion_requested_by_id` в `Request` — в списках и карточках.
- `complete` обнуляет оба поля и работает только для заказа в `Approved`; для остальных
  статусов — 422 `Invalid Order Status` (раньше «завершался» и запрос в `New`).

**Ответ:** до 1.17.0 полей `completion_requested_at` и `completion_requested_by_id` в ответах
API не было.

### 3. `updated_at` в действиях (1.17.0, 1.18.0)

**API** `sign`, `reopen`, `complete`, `request-completion` (`/orders/{id}/…`) и
`POST /requests/{id}/reject` требуют в теле `updated_at` записи, каким клиент её видел. Без него —
422; если запись с тех пор изменилась — **409** `Conflict` с `details.your_updated_at` /
`details.current_updated_at`. Сравниваются моменты времени, часовой пояс в строке не важен.
Раньше поле в этих эндпоинтах игнорировалось.

### 4. Перевод запроса в заказ, состав ТС, ошибки БД (1.18.0)

**API** Повтор типа ТС в `transport_units` (`POST /requests`, `PATCH /requests/{id}`; регистр не
важен: `20RF` = `20rf`) → **422** `Duplicate Vehicle Type`, `details.duplicate_vehicle_types`.
Ничего не сохраняется. Раньше — 500, при этом запрос оставался созданным с частью состава, а при
правке старый состав удалялся. Создание и правка запроса — в транзакции.

**API** Любое нарушение уникальности в БД, которое бэкенд не проверил заранее, теперь
**409** `Data Conflict` (`details: null`) вместо 500.

**API, без изменения контракта:** `POST /requests/{id}/approve` переводит запрос в заказ,
назначает Ops и конвертирует лида (`Lead → Active`) одной транзакцией под блокировкой — двойной
вызов больше не проходит дважды.

**Ответ** (API не менялся):
- `approve` уже возвращал запись с актуальными `client_id`, `initiator_id`, `ops_manager_id`
  и статусом. Отдельной записи «заказ» нет — это та же запись, id один; ссылок или адреса
  перехода бэкенд не возвращает.
- Подписание (`POST /orders/{id}/sign`) назначенным Ops при инициаторе-Sales работало и раньше:
  права на заказ идут от `ops_manager_id`.
- Формат `details.missing_client_fields` в `approve` не менялся.
- **Sales и `/orders`:** раздел заказов Sales закрыт и не открывается (ТЗ §2.2, §5.3.1):
  `GET /orders` — пустой список, `GET /orders/{id}` и вложенные — 403. Свою переданную запись
  Sales видит через `/requests` (`GET /requests?status=Approved,Completed`, `GET /requests/{id}`):
  карточку, маршрут с фактическими датами, переписку, файлы запроса, договоры. Документы заказа
  (накладные), финансы и счета ему не видны.
